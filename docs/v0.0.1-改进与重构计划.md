## 一、已落地代码的修复（按 ROI 排序）

### 1.1 🔴 修复流式输出（最高优先级，改动最小，收益最大）

**现状**：`server.py:64`
```python
gen = await loop.run_in_executor(None, lambda: list(engine.chat_stream(request)))
for token in gen:
    await websocket.send(...)
```
`list(...)` 把整个流式生成器物化为完整列表后才逐个 send，首 token 延迟 = 整句生成时间。

**目标**：边产边发，恢复真正的打字机效果。

**方案**：用 `asyncio.Queue` + 生产者线程 + sentinel 桥接同步生成器：
```python
queue: asyncio.Queue[str | None] = asyncio.Queue()
loop = asyncio.get_running_loop()

def _produce():
    try:
        for tok in engine.chat_stream(request):
            loop.call_soon_threadsafe(queue.put_nowait, tok)
    except Exception as exc:
        loop.call_soon_threadsafe(queue.put_nowait, exc)  # 透传异常
    finally:
        loop.call_soon_threadsafe(queue.put_nowait, None)  # sentinel

loop.run_in_executor(None, _produce)
while True:
    item = await queue.get()
    if item is None:
        break
    if isinstance(item, Exception):
        raise item
    await websocket.send(WSMessage(type="token", content=item).to_json())
```

**验证标准**：CLI 客户端首 token 出现时间 << 整句生成时间；`tok/s` 统计在生成过程中即可观察到。

---

### 1.2 🔴 统一 orchestrator 的 async 契约

**现状**：`server.py:53` 用 `async for token in orchestrator.handle_message(...)`，要求 orchestrator 返回 `AsyncIterator`。但 orchestrator 内部要调同步的 `engine.chat_stream`，桥接逻辑当前散落在 server。

**目标**：明确"谁负责同步→异步桥接"，桥接逻辑下沉、不重复。

**方案**：
- orchestrator 对外契约：`async def handle_message(text) -> AsyncIterator[str]`。
- 桥接逻辑封装为 `engine` 侧的 `async def chat_stream_async()`（内部用 1.1 的 queue 模式），server 与 orchestrator 都调它，不各自重写。
- 一旦 1.4（推理进程隔离）落地，`chat_stream_async` 自然变成跨进程流式读取，契约不变。

---

### 1.3 🟠 拆分 `ModelConfig` 职责

**现状**：`types.py:50` 把加载参数（`n_ctx`/`n_gpu_layers`/`chat_format`/`model_path`/`n_threads`/`verbose`）与采样参数（`temperature`/`max_tokens`/`stop`）混在一个 dataclass。`server.py:59` 用 `engine.config.temperature` 当回退默认，是耦合偷渡。

**目标**：加载参数与每请求可变的采样参数分离。

**方案**：
- `ModelLoadConfig`：仅含加载相关字段，`engine.load()` 时使用。
- `SamplingParams`：`temperature`/`max_tokens`/`stop`，由 `InferenceRequest` 携带。
- `engine` 不再持有采样默认值；回退模式从 `config.yaml` 的 `models` 段读取默认采样参数，而非从 `engine.config`。
- `config.yaml` 相应拆分 `models.load` 与 `models.sampling` 两个子段（向后兼容：旧平铺字段自动归入对应子段）。

---

### 1.4 🟠 配置层换 pydantic + 校验

**现状**：`main.py:78` 手抄每个字段进 dataclass，425 行 main.py 近一半是模板代码；`n_ctx` 填负数、`port` 填字符串、`temperature` 填 5.0 全部静默通过。

**目标**：一行反序列化 + 类型校验 + 路径解析 + 未知字段告警。

**方案**：
- 用 `pydantic`（或 `pydantic-settings`）重写 `AppConfig` 及各 Section。
- 路径解析用 `@field_validator`，相对路径相对 `ROOT_DIR`。
- 关键约束：`n_ctx > 0`、`1024 < port < 65536`、`0 <= temperature <= 2`、`max_tokens > 0`。
- `main.py` 的 `load_config` 收敛为 `AppConfig.from_yaml(path)` 一行。

**收益**：main.py 预计瘦身 200+ 行，配置错误在启动期暴露而非运行期崩溃。

---

### 1.5 🟠 修复 `ConversationContext._trim`

**现状**：`types.py:210` 的 trim 逻辑绕，且 messages 中混入非 user/assistant 消息（未来注入 system 记忆、tool 消息）时 `StopIteration` 静默 break，上下文无限增长。

**目标**：稳健丢弃最早一轮，对消息组成不敏感。

**方案**：
- 明确"一轮"定义：相邻的 (user, assistant) 配对，或显式按 index 区段管理。
- 简化为按段删除：维护"固定前缀（system/memory）+ 可滚动历史窗口"两段，trim 只裁历史窗口段。
- 为该函数补单元测试：覆盖规整交替、含 system 前缀、含 tool 消息、空列表四种情况。

---

### 1.6 🟡 修复 `WSMessage` 协议

**现状**：`types.py:298` 把 `extra` 用 `**` 平铺进 JSON 顶层，若 extra 含 key=`type`/`content` 会覆盖主字段；`from_json` 反向把非主字段塞回 extra。

**目标**：固定嵌套 schema，杜绝字段覆盖。

**方案**：
```json
{"type": "...", "content": "...", "extra": {...}}
```
- `to_json`：显式输出三个键，extra 嵌套。
- `from_json`：只读 `type`/`content`/`extra` 三键，其余忽略并告警。
- **注意**：此为协议变更，`test_cli.py` 的 `_dispatch` 需同步调整（它目前读 `data.get("extra", {})`，平铺时 extra 在顶层散落）。

---

### 1.7 🟡 统一时间抽象

**现状**：`types.py` 多处 `datetime.now()`，无时区，无法 mock，时间相关逻辑（recency、问候时段）不可测。

**目标**：单一时间源，可注入，显式时区。

**方案**：
- 引入 `Clock` 协议（`now() -> datetime`），默认实现用本地时区 `datetime.now(tz=ZoneInfo("Asia/Shanghai"))`。
- `MemoryItem.recency_days` / `EnvSummary.datetime_str` / `UserFact` 时间戳统一通过 `Clock` 获取。
- 测试注入假 `Clock`，可固定时间验证 recency 衰减、问候语时段分支。

### 1.9 🟡 推理互斥锁的优先级问题

**现状**：`engine.py:73` 的 `threading.Lock` 让任意时刻只有一个推理。用户对话与后台摘要/事实提取抢同一把锁，后台任务会阻塞用户响应。

**目标**：前台推理优先，后台任务让路。

**方案**：
- 短期（1.4 推理进程隔离前）：给后台任务用低优先级调度——用户推理进行时，后台任务等待；用户空闲时才跑后台摘要。
- 长期（1.4 落地后）：推理进程内部维护优先级队列，前台请求插队；或后台任务仅在 idle 时调度。

## 二、架构级重构

### 2.1 🔵 推理引擎隔离为独立子进程（核心架构决策）

**动机**：
- 模型加载 5~10s、吃满显存、可能崩；进程内单例下，模型崩 = 服务崩，热切换模型 = 服务中断。
- 同步 `llama-cpp-python` 与 asyncio 服务端的桥接脏活散落各处。
- GIL 下推理与 IO 互相影响。

**方案**：
- 新增 `inference_worker` 子进程，独占模型实例与显存。
- 主服务与 worker 通过 `multiprocessing.Queue` 或本地 socket 通信，流式 token 逐个回传。
- 主服务永远在线；worker 可独立重启、热切换模型而不中断服务。
- `engine.chat_stream_async()` 变为跨进程流式读取，对上层契约（1.2）透明。

**收益**：一次性解决 1.1/1.2/1.9 的同步异步矛盾与崩溃隔离问题。

**风险**：跨进程通信增加少量延迟（本地 queue 通常 <1ms，可接受）；需处理 worker 崩溃后的自动重启。

---

### 2.2 🟡 KV cache 复用

**动机**：架构"每轮检索记忆 → 重拼 System Prompt → 注入"，每轮重拼会让 llama-cpp-python 重新 prefill 整个 prompt，8K context 的 7B 模型每轮多花数百 ms~秒级，实时对话可感知卡顿。

**方案**：
- prompt 分层：**固定 system prefix**（角色卡 + 全局规则）+ **可变尾部**（记忆/环境/历史）。
- 固定 prefix 尽量不变，复用 KV cache；可变部分作为追加。
- 记忆注入走"伪历史"注入 history 末尾，而非污染 system prefix。
- 评估 llama-cpp-python 的 `cache_prompt` / session 复用能力。

## 三、未来模块的方向定调（实现前先定，避免返工）

### 3.1 记忆系统（`memory/`）

**避免**：纯向量 RAG 的已知缺陷——① 用户随口一句召回相关性差；② 摘要压缩不可逆丢信息；③ 时间衰减缺失。

**方向**：
- **混合检索打分**：`score = α·向量相似 + β·recency衰减 + γ·importance + δ·entity命中`。当前 `MemoryItem.recency_days()` 已算出但未进排序，必须接入打分。
- **结构化事实优先**：`UserFact`（已有雏形）走 entity memory，用户偏好/事实结构化存储，向量仅做语义召回补充。
- **分层记忆**：即时（上下文窗口）/ 短期（向量库滚动）/ 长期（SQLite 摘要）/ 事实（结构化），生命周期明确。
- **摘要可追溯**：压缩前保留原文片段，避免不可逆丢失。

### 3.2 人格系统（`personality/`）

**避免**：基于空闲时长的规则情绪状态机，在 LLM 伴侣里不自然。

**方向**：
- `Emotion` 枚举已定义好。让 LLM 在回复中**自带 emotion 标签**（function call / structured output / 文本协议标记），前端直接映射动作。
- 规则状态机仅作兜底（LLM 未输出标签时）。
- System Prompt 由"角色卡 + 当前情绪描述 + 环境"动态拼装，但固定部分与可变部分分层（配合 2.2）。

### 3.3 对话管理器（`conversation/`）

- orchestrator 对外契约见 1.2，内部编排：收消息 → 查记忆 → 拼 prompt → 推理 → 存记忆 → 回复。
- 后台任务（摘要/事实提取）调度见 1.9，前台优先。
- 空闲搭话、开机问候依赖 1.7 的 `Clock` 与 web 模块数据。

### 3.4 联网模块（`web/`）

- 网络不可用时优雅降级返回过期缓存（方向已对）。
- 抓取为同步 IO，放线程池，不阻塞 asyncio 事件循环。
- 缓存 TTL 与 `Clock` 绑定（1.7），便于测试。
